PRIVACYGUARD OSINT SUITE 3.1.0
==============================

PrivacyGuard — веб-платформа для работы с публичными техническими источниками, аудита собственных цифровых активов, сохранения результатов и локальных инструментов. Версия 3.1 расширяет предыдущую сборку документами, явным подтверждением условий в Firebase, базой знаний, источниками новостей, Security Lab, автономным Offline Lab, кодами ошибок и страницами ошибок.

ВАЖНО О ЮРИДИЧЕСКИХ ДОКУМЕНТАХ
------------------------------
В проект добавлены шаблоны:
- docs/USER_AGREEMENT_RU.md — пользовательское соглашение;
- docs/PRIVACY_POLICY_RU.md — политика конфиденциальности;
- docs/ACCEPTABLE_USE_RU.md — правила допустимого использования;
- docs/USER_GUIDE_RU.md — инструкция пользователя.

Перед публичным запуском обязательно заполни в документах и в js/legal.js:
- ФИО или юридическое наименование оператора сервиса;
- рабочий email оператора и контакт по вопросам приватности;
- юрисдикцию и применимое право;
- реальные цели и правовые основания обработки;
- фактических получателей и поставщиков данных;
- сроки хранения, резервного копирования и удаления;
- возрастные ограничения и порядок обращений пользователей.

Это стартовые шаблоны, а не юридическое заключение и не гарантия соответствия GDPR или иному закону. Фактическая конфигурация Firebase, хостинга и внешних API должна соответствовать опубликованным текстам. Перед коммерческим запуском тексты должен проверить юрист, знакомый с юрисдикцией оператора и аудиторией сервиса.

ПОДТВЕРЖДЕНИЕ ДОКУМЕНТОВ В FIREBASE
-----------------------------------
После входа новый пользователь видит обязательное окно с тремя отдельными, изначально пустыми отметками:
1. Принятие Пользовательского соглашения.
2. Подтверждение ознакомления с Политикой конфиденциальности.
3. Принятие Правил допустимого использования.

Это не маркетинговая подписка и не универсальное GDPR-согласие на любую обработку. Если оператор использует отдельные необязательные операции, основанные на согласии, для них нужно отдельное конкретное и отзывное согласие, не объединённое с общими условиями.

После нажатия «Подтвердить и продолжить» приложение записывает документ в Firestore:
users/{Firebase UID}/legalAcceptances/terms-1.0__privacy-1.0__aup-1.0

Сохраняются версии документов, отдельные булевы отметки, метод подтверждения, язык, версия приложения и серверное время Firestore. IP-адрес и пароль в журнал подтверждения не записываются. Правила запрещают изменение уже созданной записи; новый набор версий должен иметь новый идентификатор.

ОБЯЗАТЕЛЬНО:
- Опубликуй обновлённый firestore.rules в Firebase Console или через Firebase CLI.
- Если правила не опубликованы, чтение/запись подтверждения может завершиться PG-FS-403.
- Новая версия документа должна получить новую версию в js/legal.js (TERMS_VERSION, PRIVACY_VERSION или AUP_VERSION), новый ACCEPTANCE_ID и согласованные значения в firestore.rules. После этого пользователи увидят запрос на подтверждение новой версии.
- Не подменяй явные отметки предварительно установленными галочками.
- При изменении Firebase UID или удалении аккаунта журнал остаётся привязанным к соответствующему UID до удаления связанного аккаунта/данных.

ЗАПУСК
-----
1. Распакуй архив в отдельную папку.
2. Не открывай index.html через file://. ES Modules, Firebase и Service Worker требуют HTTP(S).
3. Для локального теста открой терминал в корне папки и запусти:
   python -m http.server 8080
4. Открой http://localhost:8080
5. Для установки PWA размести проект на HTTPS-хостинге, например Firebase Hosting. Service Worker не работает на обычном HTTP, кроме localhost.

FIREBASE
--------
Проект использует Firebase Authentication и Cloud Firestore. Конфигурация Web App находится в js/firebase.js.

В Firebase Console:
- Authentication → Sign-in method: включи Email/Password и Google, если они используются.
- Authentication → Settings → Authorized domains: добавь домен сайта и localhost для разработки.
- Firestore Database: создай базу в нужном регионе.
- Firestore → Rules: опубликуй firestore.rules из архива.

Для CLI (если установлен Firebase CLI и выбран верный проект):
   firebase deploy --only hosting,firestore:rules

Не заменяй правила открытыми тестовыми правилами вроде allow read, write: if true. Проверь Rules в Emulator или Rules Playground и протестируй доступ двумя разными тестовыми аккаунтами.

PWA И OFFLINE MODE
------------------
Service Worker кеширует только оболочку приложения, файлы интерфейса, локальную документацию и автономную страницу Offline Lab. Он не кеширует приватные ответы Firebase и сторонние API.

Если сеть исчезает при переходе на сайт, Service Worker показывает offline.html. Offline Lab работает автономно и содержит:
- JSON Formatter / Minifier;
- Base64 UTF-8 Encoder / Decoder;
- SHA-256;
- генератор случайных паролей;
- UUID v4;
- конвертер Unix Timestamp;
- диагностику сети, Service Worker и localStorage;
- справочник кодов ошибок.

Когда сеть вернётся, нажми «Проверить соединение» или открой основное приложение. Внешние API, вход и синхронизация Firestore по-прежнему требуют соединения.

Постоянный веб-кэш Firestore по умолчанию выключен. Включай его только на личном устройстве через чекбокс «Это моё личное устройство». Кэш может сохраняться на устройстве после выхода из аккаунта; отключение настройки применяется после перезапуска. Не включай постоянный кэш на общем компьютере или чужом телефоне. Кэш оболочки приложения и кэш пользовательских данных Firebase — разные вещи.

Кнопка «Запросить защиту локального хранилища» вызывает StorageManager.persist(), если браузер поддерживает этот API. Браузер может отказать. Это не резервная копия и не гарантия сохранности при удалении приложения/данных.

СТРАНИЦЫ ОШИБОК И КОДЫ
----------------------
Добавлены:
- 404.html — страница не найдена (PG-404);
- 403.html — доступ запрещён (PG-FS-403);
- 500.html — внутренняя ошибка (PG-APP-500);
- offline.html — автономная лаборатория / сетевой сбой (PG-NET-001).

Firebase Hosting автоматически использует 404.html для неизвестного файла/пути, если файл включён в публикацию. Реальные HTTP-статусы 403 и 500 определяет веб-сервер или backend: наличие 403.html и 500.html само по себе не заставляет любой хост возвращать статусы 403/500. Для Nginx/Apache добавлены примеры `nginx-errors.conf` и `.htaccess`; применяй их только на соответствующем сервере. Firebase Hosting использует `404.html` автоматически; для статусов 403/500 нужна настройка backend/хостинга.

Коды:
- PG-NET-001 — нет сети или запрос к источнику не выполнен;
- PG-FS-403 — Firebase/Firestore запретил доступ; проверь UID, Auth и Rules;
- PG-SRC-403 — внешний источник запретил запрос;
- PG-AUTH-401 — нужна авторизация или повторный вход;
- PG-SRC-408 — тайм-аут внешнего источника;
- PG-SRC-429 — источник ограничил частоту запросов;
- PG-SRC-502 — внешний источник вернул ошибку, либо браузер блокирует CORS;
- PG-404 — страница или ресурс не найден;
- PG-APP-500 — внутренняя ошибка приложения.

Код ошибки — подсказка для диагностики, а не замена подробного ответа сервера. Внешние источники могут использовать собственные HTTP-коды и лимиты.

---------------------
- Document Center: три версии документов, просмотр в красивом модальном окне, отдельные подтверждения и проверка записи на сервере Firestore.
- Legal Center: статус принятия действующей версии и повторный просмотр.

- NVD / CVE Quick Search: ручной поиск записей в публичном NIST NVD API. Публичный API имеет лимиты; HTTP 429 означает, что нужно подождать.
- Sources: официальные ссылки на CISA Alerts/KEV, NIST NVD, ENISA, EDPB, OWASP, MDN, Firebase и HIBP. Это ссылки на первоисточники, а не выдуманная лента; свежие новости читаются у издателя.
- Offline Lab: автономные локальные инструменты без Firebase/CDN.
- Диагностика сети, Service Worker, StorageManager и очистка только кэшей PrivacyGuard.
- Страницы 404/403/500 и единая система кодов ошибок.
- PWA install prompt для совместимых браузеров.

IPINFO TOKEN
------------
IPinfo lookup из версии 2.3 сохранён в 3.0.1/3.1 по просьбе владельца проекта. Текущий токен присутствует в браузерном JavaScript (`js/app.js`) и поэтому виден посетителям сайта. Ограничь его квоты и разрешённые сценарии в кабинете IPinfo; если поставщик позволяет — настрой ограничения по домену/сервису. Если токен когда-либо был публично опубликован, отозвать и выпустить новый можно только в кабинете IPinfo. Не используй этот ключ для серверных привилегий.

ДРУГИЕ ОГРАНИЧЕНИЯ И ВАЖНЫЕ ЗАМЕЧАНИЯ
-------------------------------------
- Monitoring в текущей версии запускается вручную. Автоматическое расписание и фоновые уведомления требуют отдельного backend, например Firebase Cloud Functions + Scheduler.
- Некоторые источники ограничивают CORS, частоту запросов или изменяют структуру ответа. Приложение должно честно показывать недоступность, а не имитировать результаты.
- Security Score не показывает фиктивную оценку, пока нет обоснованной методики.
- Security Lab выполняет запросы только после действия пользователя; не запускай массовые запросы.
- Проверяй только собственные активы или активы, на которые есть явное разрешение.
- Не вводи полные номера платёжных карт, CVV, приватные ключи, пароли от внешних аккаунтов и персональные данные третьих лиц.
- Firebase Web App config — клиентская конфигурация, но Firestore Rules и Authentication должны быть корректно настроены. Никогда не включай Admin SDK ключ в клиентский архив.

ПРОВЕРКА ПОСЛЕ УСТАНОВКИ
------------------------
1. Создай тестовую учётную запись и войди онлайн.
2. Убедись, что окно документов появилось и три галочки изначально пусты.
3. Подтверди три пункта. Проверь Firestore: users/{uid}/legalAcceptances/terms-1.0__privacy-1.0__aup-1.0.
4. Перезагрузи страницу и проверь, что подтверждение читается с сервера и повторное окно не появляется.
5. Открой «Документы и соглашения», посмотри три документа.
6. Создай проект, добавь собственный домен/IP и запусти ручную проверку.
7. Открой Security Lab: проверь DNS и сделай CVE-запрос NVD.
8. Открой Offline Lab через offline.html и протестируй JSON/Base64/SHA-256/UUID.
9. На тестовом окружении отключи сеть и убедись, что Service Worker показывает Offline Lab.
10. Проверь неизвестный URL: хост должен вернуть 404 и показать 404.html.
11. Проверь доступ к Firestore вторым аккаунтом: данные первого аккаунта должны быть недоступны.
12. Не запускай удаление аккаунта на основном профиле в ходе проверки.
